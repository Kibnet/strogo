# G02: структурная проверка пакета

`G02BuildManifest.Parse` проверяет строгий canonical `build-manifest.json` версии `strogo.build-manifest.v0.2`: закрытый набор полей, `win-x64`, digest identities, порядок и уникальность `files`, допустимые роли, обязательную кардинальность и `packageDigest` от payload без одноимённого поля. Canonical paths начинаются с `content/`, состоят из lowercase segments и исключают traversal, drive/UNC/ADS-синтаксис и имена устройств Windows. `ArtifactDigest` относится к полному manifest.

`G02PackageSnapshot.OpenStructural` проверяет ровно два root entry, перечисляет всё `content/` без перехода через reparse points, сравнивает фактические файлы и каталоги с manifest, сверяет SHA-256 и длину каждого файла. На Windows он удерживает handles корня и всех каталогов, открывает файлы через `CreateFileW(FILE_FLAG_OPEN_REPARSE_POINT, FILE_SHARE_READ)`, проверяет атрибуты **открытого handle** и его final path, затем удерживает `FileStream` для manifest и перечисленных файлов до `Dispose`. Named streams проверяются через `FindFirstStreamW`/`FindNextStreamW`. `ReadHeld(path)` возвращает bytes из уже проверенного handle для последующей проверки proof и loader; повторное открытие пути не является доверенным источником. Использованные Win32 API описаны в [Microsoft Learn: CreateFileW](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilew), [GetFinalPathNameByHandleW](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-getfinalpathnamebyhandlew), [FindFirstStreamW](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-findfirststreamw) и [структуре результата](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/ns-fileapi-win32_find_stream_data).

Этот API подтверждает только **структуру и bytes closure на момент snapshot**. Он не запрещает добавлять новые файлы в каталог после инвентаризации; последующие trusted шаги должны читать только удерживаемые bytes и повторять проверку дерева при новом admission/load, не использовать путь к пакету как свободный loader source. API не сверяет содержимое module/bundle/approval/proof между собой, не повторяет prover, не проверяет host trust, admission или пригодность generated assembly к исполнению. Создать синтетический self-consistent manifest и пройти `OpenStructural` недостаточно для `admit`, `Load` или G02 AC3. Следующий verifier должен использовать удерживаемые handles, проверить semantic identities и заново воспроизвести proof до предложения владельцу второго решения.

`G02StoredIdentityVerifier.Verify` — следующий, но **не финальный** слой. Он читает только удерживаемые snapshot bytes; сверяет canonical module и его source digest, canonical owner bundle и его domain-separated digest, host-provided ожидаемый bundle digest, signed contract approval против текущего host-owned owner state и его artifact digest. У сохранённого `proof.json` проверяются canonical JSON, точная schema/поля, идентификаторы module/bundle/approval/toolchain/closure, `Verified` outcome и obligations, их порядок и artifact digest. Возвращаемый `G02StoredIdentity` — receipt о связности данных, без verifier replay и без release admission.

Ошибки `OwnerTrust` сохраняют свои типизированные коды: неверная подпись, истёкший срок, несовпадение epoch и откат state не маскируются общим package-кодом. Проверка текущего approval предшествует сравнению остальных identity полей; при одновременно отозванном approval и неверном ожидаемом bundle сообщается отказ epoch. Receipt не удерживает snapshot за вызывающего: будущий admission/loader должен сохранять живые handles на протяжении проверки и заново читать current owner state на новом gate.

Сейчас `proofSourcesDigest`, `transcriptDigest` и `sourceMapDigest` проверяются как синтаксически корректные digests, но ещё не пересчитываются из соответствующих bytes. `proof-transcript`, source map, generated assembly и `.deps.json` пока связаны с manifest только SHA-256 и длиной. Следующий checkpoint должен установить deterministic digest conventions, заново воспроизвести prover по удерживаемым canonical inputs и сопоставить transcript/obligation vector до любой интерактивной проекции `admit`. Самосогласованный поддельный proof всё ещё пройдёт **этот промежуточный** слой, поэтому его нельзя использовать отдельно как право запуска.

Локальный conformance использует синтетические bytes, disposable RSA key и одноразовые каталоги под игнорируемым `artifacts/local-validation/g02/`. Он проверяет успешную структурную проверку, отказ при изменении bytes, лишнем файле, named stream, reparse point, неверном RID/роли/пути/порядке/digest и запрет записи в файл при удерживаемом handle. Детерминированный race-probe подменяет перечисленный файл ссылкой на внешние byte-identical bytes **после** инвентаризации и до открытия; handle-level проверка отвергает её. Отдельный identity fixture содержит настоящий canonical module/bundle и подпись disposable key, но его proof metadata самосоставлены для проверки связывания полей. Это не proof package и не release admission.
