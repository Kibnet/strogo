# G02: структурная проверка пакета

`G02BuildManifest.Parse` проверяет строгий canonical `build-manifest.json` версии `strogo.build-manifest.v0.2`: закрытый набор полей, `win-x64`, digest identities, порядок и уникальность `files`, допустимые роли, обязательную кардинальность и `packageDigest` от payload без одноимённого поля. Canonical paths начинаются с `content/`, состоят из lowercase segments и исключают traversal, drive/UNC/ADS-синтаксис и имена устройств Windows. `ArtifactDigest` относится к полному manifest.

`G02PackageSnapshot.OpenStructural` проверяет ровно два root entry, перечисляет всё `content/` без перехода через reparse points, сравнивает фактические файлы и каталоги с manifest, сверяет SHA-256 и длину каждого файла. На Windows он удерживает handles корня и всех каталогов, открывает файлы через `CreateFileW(FILE_FLAG_OPEN_REPARSE_POINT, FILE_SHARE_READ)`, проверяет атрибуты **открытого handle** и его final path, затем удерживает `FileStream` для manifest и перечисленных файлов до `Dispose`. Named streams проверяются через `FindFirstStreamW`/`FindNextStreamW`. `ReadHeld(path)` возвращает bytes из уже проверенного handle для последующей проверки proof и loader; повторное открытие пути не является доверенным источником. Использованные Win32 API описаны в [Microsoft Learn: CreateFileW](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilew), [GetFinalPathNameByHandleW](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-getfinalpathnamebyhandlew), [FindFirstStreamW](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-findfirststreamw) и [структуре результата](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/ns-fileapi-win32_find_stream_data).

Этот API подтверждает только **структуру и bytes closure на момент snapshot**. Он не запрещает добавлять новые файлы в каталог после инвентаризации; последующие trusted шаги должны читать только удерживаемые bytes и повторять проверку дерева при новом admission/load, не использовать путь к пакету как свободный loader source. API не сверяет содержимое module/bundle/approval/proof между собой, не повторяет prover, не проверяет host trust, admission или пригодность generated assembly к исполнению. Создать синтетический self-consistent manifest и пройти `OpenStructural` недостаточно для `admit`, `Load` или G02 AC3. Следующий verifier должен использовать удерживаемые handles, проверить semantic identities и заново воспроизвести proof до предложения владельцу второго решения.

`G02StoredIdentityVerifier.Verify` — следующий, но **не финальный** слой. Он читает только удерживаемые snapshot bytes; сверяет canonical module и его source digest, canonical owner bundle и его domain-separated digest, host-provided ожидаемый bundle digest, signed contract approval против текущего host-owned owner state и его artifact digest. У сохранённого `proof.json` проверяются canonical JSON, точная schema/поля, идентификаторы module/bundle/approval/toolchain/closure, `Verified` outcome и obligations, их порядок и artifact digest. Возвращаемый `G02StoredIdentity` — receipt о связности данных, без verifier replay и без release admission.

Ошибки `OwnerTrust` сохраняют свои типизированные коды: неверная подпись, истёкший срок, несовпадение epoch и откат state не маскируются общим package-кодом. Проверка текущего approval предшествует сравнению остальных identity полей; при одновременно отозванном approval и неверном ожидаемом bundle сообщается отказ epoch. Receipt не удерживает snapshot за вызывающего: будущий admission/loader должен сохранять живые handles на протяжении проверки и заново читать current owner state на новом gate.

`proofSourcesDigest` теперь вычисляется как `H("strogo.proof.v0.2/proof-sources", canonical JSON array)` из отсортированных `proof-source` manifest entries с ровно `path`, `sha256`, `length`, `role`. Каждый source читается через удерживаемый handle и проверяется как непустой строгий UTF-8 без BOM, CR и NUL. `transcriptDigest` равен `H("strogo.proof.v0.2/transcript", exact canonical transcript bytes)`, `sourceMapDigest` — `H("strogo.proof.v0.2/source-map", exact canonical source-map bytes)`. Эти G02 `v0.2` теги относятся только к production-profile прототипу; E06 validation-only использует свои `v0.1` теги.

Сохранённый transcript должен быть canonical JSON с точной схемой `strogo.proof-transcript.v0.2`, совпадающими `toolchainDigest`, `proofSourcesDigest`, `outcome` и тем же упорядоченным vector `(obligationId, kind, status, evidenceDigest)`, что в `proof.json`. Для допускаемого `Verified` vector закрытый `diagnosticCode` равен `verified`; остальные outcomes этим промежуточным verifier не принимаются. Нормализация реальных prover diagnostics ещё не реализована. Source map проверяется как canonical JSON и по digest; его семантическая связь с generated symbols, assembly и `.deps.json` пока не установлена. Эти файлы структурно связаны с manifest по SHA-256 и длине.

`G02ProofSourceRegenerator.Verify` добавляет проверку происхождения proof input: компилирует удерживаемый canonical module, связывает его с удерживаемым owner bundle через тот же lowerer, заново получает Dafny source и source map и требует точного совпадения с удерживаемыми файлами. Его нужно вызывать после `G02StoredIdentityVerifier.Verify` на том же живом snapshot. Даже если злоумышленник пересчитал transcript, proof и manifest под изменённый `.dfy` или source map, эта проверка отвергнет подмену. Пока lowerer создаёт один source и регенератор отклоняет пакет с несколькими `proof-source`; manifest и wire-контракт допускают несколько, поэтому это явное ограничение checkpoint и blocker для общего AC1/admission, а не сужение утверждённой схемы.

Следующий checkpoint должен заново воспроизвести prover по удерживаемым canonical inputs и потребовать byte-equal normalized transcript/obligation vector до любой интерактивной проекции `admit`. Самосогласованный поддельный proof с неизменённым generated source всё ещё пройдёт **этот промежуточный** слой, поэтому его нельзя использовать отдельно как право запуска.

Локальный conformance использует синтетические bytes, disposable RSA key и одноразовые каталоги под игнорируемым `artifacts/local-validation/g02/`. Он проверяет успешную структурную проверку, отказ при изменении bytes, лишнем файле, named stream, reparse point, неверном RID/роли/пути/порядке/digest и запрет записи в файл при удерживаемом handle. Детерминированный race-probe подменяет перечисленный файл ссылкой на внешние byte-identical bytes **после** инвентаризации и до открытия; handle-level проверка отвергает её. Отдельный identity fixture содержит настоящий canonical module/bundle и подпись disposable key, но его proof metadata и transcript самосоставлены для проверки связывания полей. Отдельные negative probes меняют proof source, transcript, vector и source map вместе с manifest, чтобы структура и file hashes оставались корректными; регенерация дополнительно отклоняет самосогласованную подмену source/map. Это не proof package и не release admission.

## Свежий verifier replay: исследовательская контрольная точка

Внутренние `G02DafnyToolchain` и `G02DafnyReplay` закрепляют ordinal inventory из 290 файлов, удерживают файловые handles и повторно проверяют closure, запускают Dafny с очищенным environment и ограничивают время и объём stdout/stderr. Нормативный inventory digest уточнён утверждённым erratum. Два fixture-модуля проходят реальный replay с одинаковым canonical transcript при повторе; fold-sum fixture доказательство не проходит. Подробности и отрицательные результаты: K-G02-014 в [журнале знаний](knowledge-log.md).

Этот runner пока не участвует в production admission. Необходимо связать его со signed held package и текущим owner state, сравнить сохранённые proof artifacts, обеспечить host-owned ACL и containment всего дерева процессов. Проверки fixture не заменяют отдельные D02 и release решения владельца.

Для process containment Windows x64 runner теперь использует atomic job-list startup с kill-on-close и без breakaway. Job termination охватывает descendants даже после завершения parent; bounded drain выполняется до успешного результата. Process-spy и границы evidence описаны в K-G02-015. Это не закрывает оставшиеся timeout/overflow/environment/ACL/package admission gates.

Общий `G02VerifierProcess` проверен реальными timeout/child, stdout/stderr overflow и exact-boundary probes. Environment child целиком сверяется с пятью разрешёнными переменными; test-only сокращение deadline не меняет production 55+5 секунд. Evidence и ограничения — K-G02-016. Проверенный набор process boundaries не заменяет signed package/current-state или ACL admission gates.

## Composed held fixture replay

`G02PackageProofReplay` объединяет owner/stored proof identity, deterministic regeneration и два свежих pinned replay с побайтовой сверкой held transcript/vector. Wire obligation IDs вычисляются по [утверждённой поправке](../specs/2026-09-30-g02-obligation-id-erratum-v0.2.md); source map и lowerer остаются прежними. Проверенный producer profile использует ровно `content/candidate.dfy`; альтернативный путь явно отказывает.

Положительные scalar/allocation fixtures и самосогласованные forged packages проверены отдельно (K-G02-019). Их compiled DLL/deps/closure остаются заглушками, owner подписи — disposable conformance signatures. Эта internal цепочка не предоставляет runtime admission: реальные host state freshness/ACL, compiled closure, public orchestration и отдельные D02/release решения ещё обязательны.
